# Журнал архитектурных решений (ADR)

Здесь фиксируется **почему** код такой, какой есть. PLAN.md отвечает на вопрос «что делаем»,
этот файл — «почему именно так и что отвергли». Одна запись = одно решение.
Новое решение дописывается в конец по шаблону из последнего раздела.

---

### D-01. Зоны работ — радиус вокруг центрального блока, а не список клеток

- **Дата:** 2026-10-20
- **Статус:** принято
- **Контекст:** игроку нужен инструмент «зона работ одного типа»; радиус должен меняться слайдером 64..512 клеток.
- **Решение:** зона описывается центром и радиусом; принадлежность клетки — формулой `dx²+dy² <= r²`. Покрытие для маршрутизации хранится битовой картой «клетка → id зоны» отдельно на каждый тип работ.
- **Почему не список клеток:** диск радиуса 512 — это ~823 000 клеток на одну зону. При десятках зон это гигабайты, и любая правка радиуса — перестройка миллионов элементов.
- **Последствия:** `ContainsTile` — O(1) без памяти; `ZoneCoverageMap` занимает ~2 МБ на тип работ; перечисление клеток зоны (для UI) запрещено — только формула.

### D-02. Маршрутизация работ — пуш от работы в зону, а не опрос

- **Дата:** 2026-10-20
- **Статус:** принято
- **Контекст:** целевая нагрузка — 10 000 активных агентов; работы появляются постоянно.
- **Решение:** при создании работы `JobBroker` отправляет её в зону, покрывающую эту клетку (`ZoneJobRouter.Push`, lock-free очередь на зону, O(1)). Работы вне зон отбрасываются и переотправляются раз в ~30 с.
- **Почему не опрос:** «все зоны × все работы» каждый кадр не масштабируется; кэш «кто покрывает клетку» всё равно нужен, а пуш делает горячий путь O(1).
- **Последствия:** появляется задержка до 30 с на работу, созданную до зоны; для срочных работ — отдельный путь немедленного пуша.

### D-03. Пересечение зон одного типа — партиция по числу рабочих

- **Дата:** 2026-10-20
- **Статус:** принято
- **Контекст:** игрок может поставить две зоны одного типа с перекрытием.
- **Решение:** клетка принадлежит одной зоне; при перекрытии её забирает зона с большим числом назначенных рабочих, при равенстве — с меньшим id. Разные типы работ не конфликтуют.
- **Почему так:** иначе две зоны претендуют на одну задачу и появляется гонка «кто первый», а результат зависит от порядка потоков.
- **Последствия:** партиция детерминирована и пересчитывается при изменении числа рабочих; задачи, уже стоящие в очереди усечённой зоны, остаются там (их никто не отбирает).

### D-04. Два класса агентов, число рабочих — желаемое, без потолка

- **Дата:** 2026-10-20
- **Статус:** принято
- **Контекст:** нужно разделить «работяг» и «специалистов, привязанных к рабочему месту».
- **Решение:** `Laborer` берёт любую неквалифицированную работу, которая не отдана рабочим; `Worker` привязан к своей зоне и берёт только её задачи. Слайдер «рабочие» задаёт желаемое число; жёсткого максимума нет.
- **Почему без потолка:** ёмкость должны давать станки и рабочие места (в будущем: 10 станков × 2 места = 20 рабочих), а не константа в коде.
- **Последствия:** `WorkerAssignmentSystem` умеет расширять и сжимать набор (лишние возвращаются в разнорабочие); пустая зона не имеет территории, пока в неё не придут рабочие.

### D-05. Прерывание работы нуждой сохраняет прогресс

- **Дата:** 2026-10-20
- **Статус:** принято
- **Контекст:** агент с потребностями бросал работу, и она начиналась с нуля.
- **Решение:** задача возвращается в очередь зоны, дробный прогресс хранится по клетке (`CellProgressStore`, 0..1) и переживает сейв.
- **Почему:** иначе агент попадает в цикл «голоден → бросил → начал заново» и не достраивает объект никогда.
- **Последствия:** обработчики работ обязаны восстанавливать прогресс в `OnStart` и сохранять в `OnCancel`; сброс прогресса при отмене запрещён.

### D-06. Иерархический отрицательный ответ в индексе работ

- **Дата:** 2026-10-20
- **Статус:** принято
- **Контекст:** агент, у которого все работы на кулдауне недостижимости, каждый кадр сканировал все чанки: 5 850 мкс на промах при 100k работ.
- **Решение:** у каждого чанка считается «сколько работ не на кулдауне», плюс глобальный счётчик; при нуле поиск прекращается за O(1).
- **Почему безопасно:** флаги используются только как отсечение — они не могут объявить живую работу недоступной (инвариант `hidden == 0`).
- **Последствия:** промах 0,04 мкс (ускорение ×146 000); состояния учёта обязаны вестись парными CAS-переходами, а замена массива флагов защищена quiesce/inFlight (Dekker), иначе счётчики дрейфуют.

### D-07. Пасфайндер — HPA*, а не A*, с обязательными порогами приёмки

- **Дата:** 2026-10-20
- **Статус:** принято
- **Контекст:** мир 1024×1024 со стенами, реками и тысячами агентов.
- **Решение:** HPA* (регионы 16×16, порталы, кэш сегментов, октильная эвристика), сглаживание с ограниченным окном.
- **Почему:** линейный A* на 10 000 агентов не влезает в кадр.
- **Последствия:** приёмка — 10 000 случайных путей длиной ≥250 клеток, включая водные преграды; защита от «обхода по кругу» через нижнюю оценку `k·L`; за кадр не более 17 поисков и ≤1,5 мс.

### D-08. Производительность без отрезания функциональности

- **Дата:** 2026-10-20
- **Статус:** принято
- **Контекст:** требование «1–2 мс на кадр» при живой симуляции.
- **Решение:** разрешены только математические/алгоритмические улучшения и амортизация (размазывание работы по кадрам: «−0,5 каждые 50 кадров» вместо «−0,01 каждый кадр»). Сокращать дальности, количество агентов или возможности — запрещено.
- **Почему:** «оптимизация» удалением функций — это не оптимизация, а сокращение игры.
- **Последствия:** бюджеты вводятся как очереди/бюджеты поиска, а не как урезание логики; замеры обязаны подтверждать, что выигрыш не куплен функциональностью.

### D-09. Сохранение мира — дельта на остров с переигрыванием

- **Дата:** 2026-10-20
- **Статус:** принято
- **Контекст:** мир процедурный и огромный; полный снапшот дорог, а правки игрока терять нельзя.
- **Решение:** дельта-файл на остров (`ISM1`: магия, версия, сид, список `{X,Y,Kind,Len,payload}`), при загрузке — переигрывание поверх сгенерированного мира. Запись только при выходе, атомарная замена через `.tmp`.
- **Почему:** детерминированная генерация + дельта дают маленький сейв и полную обратимость.
- **Последствия:** любое новое изменяемое состояние обязано иметь `WorldDeltaKind` и обработчик в `IslandStateReplay`; регресс-тест требует «повторное применение дельты не даёт эффекта».

### D-10. Инструмент анализа кода должен отвечать агенту, а не только рисовать граф

- **Дата:** 2026-10-21
- **Статус:** принято
- **Контекст:** визуализатор был GUI для человека; агент искал зависимости грепом и «на глаз».
- **Решение:** `vizcore.py` (индекс + запросы), `viz_cli.py` (JSON), `viz_mcp.py` (MCP-сервер с 15 инструментами): callers/callees, impact файла и impact по git diff, циклы, мутаторы состояния, мёртвый код, висячие ссылки сцен, карта конкурентности, горячий путь, нарушения слоёв, покрытие тестами, дрейф PLAN.md.
- **Почему:** вопрос «что затронет правка файла X» решается графом за миллисекунды, а не чтением кода; при параллельной работе агентов это ещё и способ развести скоупы.
- **Последствия:** связи строятся по однозначным символам (символ, объявленный в нескольких файлах, ребра не даёт) — меньше связей, но каждая настоящая; файл в цикле сильной связности помечается, потому что его impact завышен.
